# codex MCP v2 (app-server bridge) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace the bulldozer codex MCP module's v1 (`codex exec` wrapper, non-interactive) with a bidirectional bridge over `codex app-server` that delivers correct interactive approvals (fixes codex#18268) and resume — in-session always, cross-session contingent on the Task 1 gate (else descoped to in-session) — through one MCP tool.

**Architecture:** A zero-dependency Python stdio MCP server (`mcp/codex_server.py`) that is BOTH an MCP server facing Claude Code AND a JSON-RPC client driving a persistent `codex app-server` child. A two-fd `select` reactor multiplexes CC-stdin and app-server-stdout; approvals are bridged app-server→`elicitation/create`→CC and back. Resumable threads are non-ephemeral (on-disk rollout).

**Tech Stack:** Python 3 stdlib only (`json`, `os`, `select`, `subprocess`, `sys`, `tempfile`, `shutil`); pytest; `codex` CLI 0.141.0 (`codex app-server`, stdio JSONL "jsonrpc_lite" — the `"jsonrpc"` field is OMITTED).

## Global Constraints

- **Spec:** `docs/superpowers/specs/2026-06-18-codex-mcp-v2-app-server-bridge.md` (authoritative).
- **Protocol source of truth:** the generated TS types for the INSTALLED codex 0.141.0, snapshotted at `/0/SANDBOX/CODEX-SETTINGS/codex-schema-0.141-experimental/` (top-level + `v2/` subdir — the v2 thread API types `ThreadStartParams`/`ThreadResumeParams`/`TurnStartParams`/`UserInput`/`SandboxMode`/`SandboxPolicy` live in `v2/`). Regen with `codex app-server generate-ts --experimental --out <dir>`. NOTE: `UserInput` text variant field is `text_elements` (snake_case, required but serde-defaults to empty). `ThreadResumeParams` in 0.141 DOES expose `path`/`history` but both are `[UNSTABLE]` and `history` is "FOR CODEX CLOUD - DO NOT USE"; precedence history > non-empty path > threadId; schema says "Prefer using thread_id whenever possible" → by-id remains primary.
- **Zero runtime dependencies** — Python stdlib only (matches v1; cold-start matters, server spawned per session).
- **stdout = JSON-RPC frames ONLY.** All logging → stderr (or a file). Violating this corrupts the MCP channel.
- **app-server envelope is "jsonrpc_lite":** request `{id,method,params?}`, notification `{method,params?}`, response `{id,result}`, error `{id,error}` — NO `"jsonrpc"` field. (The CC-facing leg DOES use standard JSON-RPC 2.0 with `"jsonrpc":"2.0"`.)
- **Fail-graceful:** absent `codex` binary or app-server spawn failure → clean error result, never a crash (carried from v1).
- **INVARIANT:** every request-with-`id` on EITHER leg gets a terminal response in its own schema; never dropped, never wrong-shaped.
- **Isolation:** resumable threads are NON-ephemeral; isolation via `baseInstructions`+`config`, never `ephemeral:true`.
- **codex binary:** `JAINE_CODEX_BIN` env override else `shutil.which("codex")` else `/opt/homebrew/bin/codex`.

```python
class JsonRpcStream:
    def __init__(self): self._buf = b""
    def feed(self, chunk: bytes) -> list:
        self._buf += chunk
        out = []
        while b"\n" in self._buf:
            line, self._buf = self._buf.split(b"\n", 1)
            line = line.strip()
            if not line: continue
            try: out.append(json.loads(line))
            except json.JSONDecodeError: pass  # logged by caller
        return out

def classify(msg: dict) -> str:
    has_method = isinstance(msg, dict) and "method" in msg
    has_id = isinstance(msg, dict) and "id" in msg
    has_result = isinstance(msg, dict) and ("result" in msg or "error" in msg)
    if has_method and has_id: return "request"
    if has_method and not has_id: return "notification"
    if has_id and has_result and not has_method: return "response"
    return "invalid"
```

> **0.141 DRIFT (verified vs schema, supersedes the 0.140 plan):**
> `CommandExecutionRequestApprovalParams` in 0.141 **DOES have `availableDecisions?: Array<CommandExecutionApprovalDecision>`** ("Ordered list of decisions the client may present"). So the server now tells us exactly which decisions to offer.

> The decision union (`CommandExecutionApprovalDecision`), response `{decision: <union>}`, `FileChange` decision (string-only enum), `Permissions` response (`{permissions, scope, strictAutoReview?}` — its OWN schema), and legacy `ReviewDecision` (`approved`/`approved_for_session`/object variants/`denied`/`timed_out`/`abort`) are all confirmed vs the 0.141 schema.
